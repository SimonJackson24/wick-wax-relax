2.2 Critical Findings

[CRITICAL] Auth token stored in wrong location — order confirmation is broken for all users
CRITICAL

frontend/pages/order-confirmation.js:30

const token = localStorage.getItem('token');  // ← WRONG

The backend stores JWT as an httpOnly cookie (auth.js:136-137), not in localStorage. This means order-confirmation.js will ALWAYS fail to find a token and redirect every confirmed-order user to the login page, even though their order was just successfully placed.

The correct approach is to use the cookie-based auth that all other authenticated pages use via AuthContext. The order confirmation page needs to use the /api/orders/:id endpoint which reads the auth cookie — NOT a localStorage token.

Impact: CRITICAL — Every customer who completes checkout gets kicked to login on the confirmation page. This is a catastrophic UX failure.

Fix: Remove the localStorage token lookup entirely. The orders.js endpoint already reads req.cookies.accessToken. After a successful checkout POST to /api/orders, the response should include the order details so the redirect carries them without needing a separate fetch.
[CRITICAL] Duplicate route registration — unpredictable routing
CRITICAL

backend/server.js:114-120

app.use('/api/inventory', require('./routes/inventory'));   // line 114
app.use('/api/admin', require('./routes/admin'));           // line 116
app.use('/api/admin/settings', require('./routes/settings')); // line 117
app.use('/api/inventory', require('./routes/inventory'));   // ← DUPLICATE (line 118)
app.use('/api/admin', require('./routes/admin'));           // ← DUPLICATE (line 119)
app.use('/api/admin/settings', require('./routes/settings')); // ← DUPLICATE (line 120)

Impact: Unpredictable routing — the second registration shadows the first. Any middleware added between lines 114-117 gets bypassed by the duplicate registrations at 118-120.

Fix: Remove lines 118-120 entirely.
[CRITICAL] Payment integration is stubbed — orders are free
CRITICAL

frontend/pages/checkout.js:53  |  backend/routes/orders.js:65

The checkout page accepts payment methods APPLE_PAY, GOOGLE_PAY, KLARNA, CLEARPAY but the actual payment processing is never invoked. The order is created via orderService.createOrder() but there is no call to Stripe, Revolut, or any payment gateway to actually charge the customer. The revolutService exists but is only called in the webhook handler, not in the order creation flow.

Impact: CRITICAL — Orders can be created with a success response without any money changing hands. Business-critical gap.

Fix: Integrate Stripe or Revolut payment intent creation before order confirmation. The checkout flow must create a payment intent, collect card details via Stripe Elements / Revolut, confirm payment, then create the order record only on successful payment capture.

2.3 High Findings

[HIGH] Password reset token stored in plaintext — unlike refresh tokens
HIGH

backend/routes/auth.js:430-438

const resetToken = crypto.randomBytes(32).toString('hex');  // plaintext token
await query('UPDATE users SET reset_token = ?, reset_token_expires = ? ...',
  [resetToken, resetTokenExpires.toISOString(), user.id]);

Unlike refresh tokens (which are SHA-256 hashed before storage at auth.js:132), the password reset token is stored as plaintext. If the database is compromised, attackers can use any reset token directly to change passwords.

Fix: Hash the reset token: crypto.createHash('sha256').update(resetToken).digest('hex'). Verify by hashing the received token before DB lookup.
[HIGH] Redis configured but never used
HIGH

backend/.env.example

REDIS_URL, REDIS_HOST, REDIS_PORT, REDIS_PASSWORD are defined but the codebase has no Redis imports anywhere. The cacheService.js files exist but use in-memory caching.

Fix: Either implement Redis properly (add ioredis import to cache service) or remove Redis configuration from .env.example to avoid production misconfiguration.
[HIGH] CSP unsafe-inline for styles weakens XSS protection
HIGH

backend/server.js:21

styleSrc: ["'self'", "'unsafe-inline'"],

Allows inline styles site-wide, significantly worsening any XSS attack by enabling CSS injection.

Fix: Use 'unsafe-hashes' with explicit hashes for MUI's critical inline styles, or migrate to CSS modules to eliminate the need for unsafe-inline entirely.
[HIGH] Wrong login redirect URL — 404 page after order confirmation
HIGH

frontend/pages/order-confirmation.js:32

router.push('/account/login');  // ← 404, page is at /auth/login
Fix: Change to router.push('/auth/login').
[HIGH] DATABASE_URL in .env.example points to SQLite but code uses PostgreSQL
HIGH

backend/.env.example:2

DATABASE_URL=wick_wax_relax.db  // ← SQLite filename, but pg (PostgreSQL) is used

The database.js uses pg with individual DB_HOST, DB_PORT, DB_USER, DB_PASSWORD, DB_NAME. DATABASE_URL is never read by the actual code.

Fix: Replace DATABASE_URL in .env.example with the correct PostgreSQL variables: DB_HOST, DB_PORT, DB_USER, DB_PASSWORD, DB_NAME.

HIGH

frontend/components/SEOHead.js  |  frontend/pages/product/[id].js

SEOHead.js generates Organization schema for all pages. Product pages should include Product JSON-LD with price, availability, rating, and brand. The product prop exists in SEOHead but is not passed from the product detail page.

HIGH

frontend/public/sitemap.xml

Static entries only. Every product and category page needs its own entry for Google to discover them.

Fix: Install and configure next-sitemap to auto-generate from the product database. A next-sitemap.config.js exists but appears not to be wired into the build process.

HIGH

frontend/pages/subscriptions.js:309-342

A 20-question FAQ section with no structured data means Google cannot display these as rich snippets.
