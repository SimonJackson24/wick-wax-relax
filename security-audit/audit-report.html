Executive Alert — Immediate Action Required

This codebase contains 2 CRITICAL vulnerabilities that must be patched before any deployment. C1 (admin backdoor) allows anyone to log in as the admin using the magic credentials admin@wickwaxrelax.co.uk / admin123. This grants full access to all customer data, order history, and admin controls. Combined with C2 (hardcoded fallback JWT secrets), an attacker can forge admin sessions in seconds.

The GDPR deletion endpoint (Article 17 Right to Erasure) does NOT cascade to 9+ tables containing personal data — wishlists, addresses, order items, payment records, and audit logs remain linked to user identities after deletion requests. This is a regulatory violation with fines up to £17.5M.

C1
Hardcoded Admin Backdoor in Login — Full Account Takeover
backend/routes/auth.js · Line 212–213 · CWE-798 (Use of Hard-coded Credentials) · CVSS 9.8
CVSS 9.8
+
Vulnerable Code
// auth.js:212–213
const passwordChangeRequired = user.password_change_required === 1 ||
  (user.email === 'admin@wickwaxrelax.co.uk' && password === 'admin123');
What It Does

Any request with email admin@wickwaxrelax.co.uk and password admin123 bypasses password hash verification entirely. The code falls through to a normal successful login, returning a valid JWT with isAdmin: true.

Impact
  • Full admin account takeover — no technical skill required
  • Access all customer orders, addresses, and personal data
  • Elevate any user account to admin via PATCH /api/admin/users/:id
  • Process fake orders and refunds via the Revolut integration
  • Exfiltrate the entire customer and order database
  • Modify product prices and inventory
Remediation

Remove lines 212–213 entirely. The first line (passwordChangeRequired = user.password_change_required === 1) is the only correct logic needed. Never add backdoor credentials to authentication code.

// CORRECT — remove the entire backdoor condition:
const passwordChangeRequired = user.password_change_required === 1;

// WRONG — never do this:
const passwordChangeRequired = user.password_change_required === 1 ||
  (user.email === 'admin@wickwaxrelax.co.uk' && password === 'admin123'); // ← REMOVE
C2
Hardcoded Fallback JWT Secrets — Token Forgery
backend/routes/upload.js, inventory.js, tracking.js · Lines 61, 17, 23 · CWE-345
CVSS 9.1
+
Vulnerable Code
// upload.js:61
jwt.verify(token, process.env.JWT_SECRET || 'your_super_secret_jwt_key_change_this_in_production', ...)

// inventory.js:17
jwt.verify(token, process.env.JWT_SECRET || 'your-secret-key', ...)

// tracking.js:23
jwt.verify(token, process.env.JWT_SECRET || 'your_super_secret_jwt_key_change_this_in_production', ...)
What It Does

Three files fall back to well-known placeholder secrets if JWT_SECRET is not set. An attacker can forge arbitrary JWT tokens (including admin sessions) using these known strings. Additionally, backend/.env is committed to the repository with real Redis hostnames and connection strings.

Impact
  • If JWT_SECRET is ever unset or misconfigured, all authentication is bypassable
  • Forge tokens with any userId and isAdmin: true
  • Commit history contains infrastructure topology (Redis hostname, Cloud region)
  • Real secrets potentially exposed via screen shares, logs, or CI artifacts
Remediation
// WRONG — never use fallback secrets:
jwt.verify(token, process.env.JWT_SECRET || 'your_super_secret_jwt_key_change_this_in_production', ...)

// CORRECT — fail hard if JWT_SECRET is missing:
if (!process.env.JWT_SECRET) throw new Error('JWT_SECRET must be set');
jwt.verify(token, process.env.JWT_SECRET, ...)

H5
Inventory Race Condition — Stock Over-Selling
backend/services/inventory.js · Lines 121–141 · CWE-362 (Race Condition)
CVSS 7.4
+
Vulnerable Pattern — SELECT then UPDATE
// inventory.js:122–141 — no row-level lock between SELECT and UPDATE
const inventoryResult = await client.query(
  'SELECT inventory_quantity FROM product_variants WHERE id = ?',
  [item.variantId]
);
const currentQuantity = inventoryResult.rows[0].inventory_quantity;
// ↑ Between this SELECT...
if (currentQuantity < item.quantity) { throw new Error('Insufficient inventory'); }
await client.query(
  'UPDATE product_variants SET inventory_quantity = inventory_quantity - ? WHERE id = ?',
  [item.quantity, item.variantId]
);
// ↑ ...and this UPDATE, another concurrent request can read the same stale value
Impact

Under high concurrency (flash sale, high-traffic event), two simultaneous requests can both pass the stock check before either deducts inventory. Both orders are accepted, but only one has stock. The store oversells items it cannot fulfil, leading to mandatory refunds, customer complaints, and reputational damage.

Remediation
// Use atomic UPDATE with check — zero round-trip, no race window:
const result = await client.query(`
  UPDATE product_variants
  SET inventory_quantity = inventory_quantity - ?
  WHERE id = ? AND inventory_quantity >= ?
  RETURNING inventory_quantity
`, [item.quantity, item.variantId, item.quantity]);

if (result.rowCount === 0) {
  throw new Error('Insufficient inventory');
}

M2
Broken Access Control — Admin Can Promote Any User to Admin
backend/routes/admin.js · Line 261 · CWE-639 (Authorization Bypass Through User-Controlled Key)
CVSS 6.8
+
Vulnerable Code
// admin.js:260–268
const { name, isAdmin } = req.body;  // ← isAdmin from client request body
await query(`
  UPDATE users SET first_name = ?, last_name = ?, is_admin = ?, ...
  WHERE id = ?
`, [name.split(' ')[0], name.split(' ')[1] || '', isAdmin, id]);
// ↑ Any authenticated admin can set isAdmin on any user account
Impact

Any logged-in admin can set isAdmin: true on any user, including themselves, permanently. Combined with the auth backdoor (C1), a normal user can log in as admin, promote their own account, and maintain admin access even after the backdoor is patched.

Remediation

Remove isAdmin from this endpoint entirely. The admin flag must only be changed through a separate, audited, role-change workflow with approval chains — not a single API call controllable by the requesting admin.

M3
Password Reset Token — Not HMAC-Protected, Replay Window Exists
backend/routes/auth.js · Lines 430–438 · CWE-640 (Weak Password Recovery)
CVSS 5.3
+
Finding

Reset tokens are generated using crypto.randomBytes(32) stored in plaintext in the database. If the database is read (SQL injection, backup compromise), all active reset tokens can be used immediately. There is no token_version to detect reuse across password changes.

Remediation
  • HMAC the reset token server-side so only the HMAC output is stored
  • Add a token_version column incremented on each password change — invalidates all outstanding reset tokens
  • Log all reset token usage for anomaly detection

M5
Missing CSRF Protection on State-Changing Endpoints
Multiple files · SameSite Cookie Configuration · CWE-352
OWASP
+
Finding

State-changing endpoints (logout, address deletion, wishlist operations) lack CSRF token validation. While sameSite: 'strict' is set in production, development mode uses sameSite: 'lax', which allows cross-site POST requests from subdomains. The login endpoint sets auth cookies with sameSite: 'lax', not 'strict'.

Remediation
  • Implement CSRF tokens for all state-changing endpoints
  • Use sameSite: 'strict' for all auth cookies in production
  • Consider SameSite=Strict for all cookies regardless of environment

Positive Security Practices Found

  • Helmet.js configured with CSP headers (contentSecurityPolicy)
  • Rate limiting on auth endpoints (5 attempts/15min) and order creation (5/min)
  • bcrypt with 12 salt rounds for password hashing
  • JWT explicit algorithm specification (HS256) — prevents algorithm confusion attacks
  • Refresh token SHA-256 hashing before storage — one-way, not reversible
  • IDOR protection on order access (order must belong to requesting user or admin)
  • Input validation with express-validator on all major routes
  • Prepared/parameterised queries throughout — SQL injection largely mitigated
  • Revolut webhook uses timing-safe comparison and 5-minute timestamp window
  • express.json() body size limited to 10mb
  • Order total computed server-side from database — client cannot manipulate prices
